# False Positive Log

This document records benign activity that triggered K8s Sentinel detection rules during baseline testing and validation.

The purpose of this log is to distinguish expected Kubernetes or container activity from suspicious behavior and to document detection tuning decisions.

---

## 1. Rule 1 — Kubernetes Infrastructure Command Execution

### Rule

**K8s Sentinel Container Exec**

```text
K8s Sentinel detected command execution in a container
```

### Detection Rule

The original Rule 1 condition was:

```yaml
condition: >
  evt.type in (execve, execveat)
  and container.id != host
```

This rule detects command execution inside containers.

### Observed False Positive

During the Day 11 baseline capture, Rule 1 repeatedly generated alerts for normal Kubernetes infrastructure activity.

Observed processes included:

```text
iptables
ip6tables
```

The activity was associated with Kubernetes networking components such as:

```text
kube-proxy
kindnet-cni
```

Example activity included commands such as:

```text
iptables -t nat -S --wait
iptables -t nat -C KIND-MASQ-AGENT ...
iptables -t nat -C POSTROUTING ...
iptables -w 5 -S KUBE-PROXY-CANARY -t mangle
ip6tables -w 5 -S KUBE-PROXY-CANARY -t mangle
```

These events were repeatedly observed during the baseline period.

### Why It Was Considered Benign

The observed activity was generated by Kubernetes networking components performing normal networking and iptables configuration/check operations.

The events did not represent an attack against the test workloads.

Therefore, these alerts were classified as **false positives for the purpose of the K8s Sentinel application-level detection baseline**.

### Metadata Limitation

Some of the observed events contained incomplete Kubernetes metadata:

```text
container=<NA>
image=<NA>
k8s_pod=<NA>
k8s_namespace=<NA>
```

For example:

```text
process=iptables
container=<NA>
k8s_pod=<NA>
k8s_namespace=<NA>
```

Because the namespace field was unavailable for these events, a condition based only on:

```yaml
not k8s.ns.name=kube-system
```

could not suppress every infrastructure event with `<NA>` metadata.

### Tuning Applied

Rule 1 was updated to exclude events explicitly identified as belonging to the Kubernetes system namespace:

```yaml
condition: >
  evt.type in (execve, execveat)
  and container.id != host
  and not k8s.ns.name=kube-system
```

The purpose of this change was to reduce expected Kubernetes system activity while keeping detection enabled for application workloads in the `default` namespace.

### Validation After Tuning

After the rule was updated and Falco was upgraded, the Falco agents on both nodes returned to:

```text
2/2 Running
```

A test command was then executed inside the K8s Sentinel `hostpath-pod`:

```bash
kubectl exec hostpath-pod -- sh -c 'echo K8S_SENTINEL_RULE1_FINAL_TEST'
```

The command produced:

```text
K8S_SENTINEL_RULE1_FINAL_TEST
```

Falco subsequently generated a Rule 1 alert containing:

```text
process=sh
command=sh -c echo K8S_SENTINEL_RULE1_FINAL_TEST
container=hostpath-container
k8s_pod=hostpath-pod
k8s_namespace=default
technique_id=T1609
tactic=Execution
```

This confirmed that the tuning did **not** disable Rule 1 detection for the intended `default` namespace test workload.

### Result

**Status: TUNED AND VALIDATED**

The rule continues to detect command execution in the intended test workload while explicitly excluding Kubernetes system-namespace activity when namespace metadata is available.

Infrastructure events with `<NA>` Kubernetes metadata remain a known limitation.

---

## 3. Tuning Principle

The baseline exercise showed that a broad process-execution rule can generate significant noise in a Kubernetes environment.

The detection should therefore distinguish between:

1. Kubernetes infrastructure activity that is expected during normal cluster operation.
2. Command execution occurring inside the intentionally vulnerable application/test workloads.

The tuning was designed to reduce the first category without removing detection coverage for the second category.

---

## 4. Known Limitation

Some Falco events observed during the baseline contained incomplete Kubernetes metadata, represented by:

```text
<NA>
```

For these events, the rule cannot reliably determine the Kubernetes namespace.

Therefore, the current tuning should not be interpreted as eliminating all possible infrastructure-related Rule 1 alerts.

The current configuration instead provides a more targeted baseline while retaining detection coverage for the K8s Sentinel test workloads.

## 5. Day 11 Result

Day 11 baseline analysis identified a clear false-positive source in the broad container-execution rule.

The Rule 1 condition was tuned to exclude explicitly identified Kubernetes system-namespace activity, and the detection was subsequently validated against `hostpath-pod` in the `default` namespace.

**Rule 1: Tuned and validated.**
